# Производство: минимум по разнообразию, потом избыток по уровню ТУ

> По прямому запросу пользователя (2026-08-22): раньше `produceHour` (`server/production.go`) перебирал ВСЕ рецепты завода (любого уровня ТУ) в равной ротации по часам — на практике это означало, что дешёвый ТУ1 забирал сырьё каждый час просто потому, что почти всегда по карману, а ТУ2/ТУ3 почти никогда не успевали накопить нужное сырьё до следующего захода дешёвого ТУ1. Первая правка ввела приоритет по уровню ТУ (от дорогого к дешёвому, см. историю ниже) — но она заботилась только о том, чтобы ТУ2/ТУ3 не голодали, а не о том, чтобы завод выпускал РАЗНООБРАЗИЕ типов. Завод мог всю игру качать один и тот же доступный ТУ3-рецепт, пока сосед по цеху стоял на нуле. Вторая правка (эта) вводит явную цель разнообразия: **сперва добрать каждому типу компонента хотя бы 10 штук на складе, и только потом — качать избыток**.

## Текущий алгоритм (`pickRecipeToProduce`, `server/production.go`)

Каждый час, для каждого завода — два прохода:

1. **Фаза минимума** (`pickBelowFloor`) — есть ли у завода хоть один тип компонента (**любого** ТУ), чей запас на складе ниже `componentStockFloor = 10`? Если да — производим именно его. Ротация по часам идёт сразу по ВСЕМ дефицитным типам вперемешку (не по уровням ТУ отдельно): дорогой ТУ3-рецепт, которому ещё не хватает собственных ТУ1/ТУ2-входов, просто не пройдёт проверку на сырьё — ротация автоматически перескочит на следующий дефицитный тип. Дешёвые типы закрываются раньше дорогих сами по себе, без явного порядка по ТУ.
2. **Фаза избытка** — если по ВСЕМ типам этого завода запас уже ≥ 10 (дефицита нет), качаем избыток тем же приоритетом, что раньше: сначала ТУ3, если не по карману — ТУ2, если и это не по карману — ТУ1. Отдельный «ТУ1-гейт» (раньше `tier1NeedsBuildup`) больше не нужен — фаза минимума уже гарантирует, что ТУ1 никогда не будет забыт вовсе.

Внутри одной фазы — та же почасовая ротация, что и раньше (сдвиг перебора на номер текущего часа), несколько рецептов по очереди получают первый шанс.

Соответствует клиентскому полю «мин. запас» на складе (`client/planet.html`, `whState`) — там оно пока чисто косметическое/сессионное число на UI, здесь то же значение (10) зашито как единый порог для всех компонентов на сервере.

## Что не учтено

- **Порог `componentStockFloor = 10`** — единое число для абсолютно всех компонентов, всех ТУ, не настраивается по типу. Возможно, для очень ходовых компонентов (Металлоконструкции) стоило бы иметь порог выше, чем для дефицитных (Химреагенты) — не сделано, ждёт отдельного решения, если понадобится.
- **monarchy и technocracy по-прежнему не сдвинули Химзавод с нуля** — это не про приоритет производства, а про физическую нехватку конкретного сырья (вода/инертные газы) именно на этих процедурно сгенерированных планетах: фаза минимума честно пытается произвести хим.реагенты каждый час, но `canAffordCycle` проваливается — сырья просто нет на складе.
- **Внутризаводская конкуренция за общее сырьё между уровнями ТУ** по-прежнему есть внутри одной фазы (например, Металлоконструкции нужны и напрямую ТУ1, и как вход в ТУ2/ТУ3) — почасовая ротация распределяет по очереди, но не гарантирует идеальный баланс, если несколько типов одновременно по карману.
