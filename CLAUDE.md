## Структура проекта

- `ТЗ.md` — новое техническое задание (механика/симуляция/экономика/фракции), наполняется по ходу обсуждения.
- `ТЗ_UI.md` — техническое задание по интерфейсу игрока (HUD, экраны, взаимодействия).
- `ТЗ_Ресурсы.md` — номенклатура сырья (17 видов), цепочки переделов (21 компонент I/II/III цикла), шахты, орбитальные станции и сборщики у аномалий. Два ресурса получаются с расходом других: металлический водород (газовые гиганты у центра) и антиматерия (чёрные дыры и нейтронные звёзды) — они заменили «экзотическую материю», а металлический заодно и «дейтерий» как топливо лучших двигателей.
- `ТЗ_Корабль.md` — классы кораблей (палубы/модули по классу), рецепты палубы/брони/19 модулей/8 типов оружия/уникальных построек Станции (Ускоритель/Портал/Луч смерти). Рецепты (в компонентах) заведены в `server/economy.go` (`shipItemCosts`) ради спроса на ресурсы — но постройка/бой/палубы как игровая механика по-прежнему чисто теория, в коде их нет (`server/ship.go` знает только один глобальный корабль без структуры), см. открытые вопросы в конце файла.
- `ТЗ_Экономика.md` — перенесённый внешний документ по экономике колонии: 4 шахты и 4 завода (без уровней у шахт, ТУ1–ТУ3 у заводов), рецепты и лимитирующие ресурсы производства по уровням, население/поселения (лимит по разнообразию пищи, рост/убыль ±1 в сутки), стоимость и содержание 20 типов зданий, эталонный расчёт «стандартной колонии». Число гексов в документе (41) расходится с реализованным (19/37/61 по размеру планеты, ТЗ_UI.md §5.1) — см. примечание в шапке файла.
- [`Расчёт_производственных_мощностей.md`](Расчёт_производственных_мощностей.md) — сколько заводов каждого типа объективно нужно, чтобы переработать в ТУ1-компоненты всё, что добывают 40 шахт (10 каждого из 4 типов, эталон ТЗ_Экономика.md §7/§9.1), при потолке `maxProductionBatchesPerDay=12` партий/сутки на завод (`server/production.go`). Число получено симуляцией (`server/production_calc_test.go`), не ручным расчётом — учитывает реальную конкуренцию за общее дефицитное сырьё (инертные газы делят Химзавод и Электрозавод), поэтому немного расходится с независимым расчётом ТЗ_Экономика.md §8.5. Итог: 5 Металлургических + 4 Химических + 1 Электроинженерный + 1 Лаборатория передовых систем = 11 заводов, все 4 — теперь честно выведены из расчёта ТУ1 (после переноса «Научного оборудования» с Электрозавода на Лабораторию, см. `economy.go`/`server/production.go` ниже, Лаборатория тоже получила рецепт ТУ1 и попадает в расчёт наравне с остальными) — без учёта дальнейшего ТУ2/ТУ3-масштабирования и содержания зданий, см. оговорки в файле.
- `server/` — Go-сервер v2: единые часы игрового времени, авторитетная симуляция сектора, раздача `client/` (в том числе на телефон по локальной сети). Подробности и API — в [`server/README.md`](server/README.md).
  - `server/clock.go` — единое время: `months += speed × Δt`, ускорение меняет только множитель.
  - `server/galaxy.go` — генератор (зоны, рукава, массы, кривая скорости по орбитам), перенесён из клиента.
  - `server/sim.go` — жизненный цикл объектов: очередь выходов, оборот с возвратом массы, события.
  - `server/planets.go` — заселение звёзд планетами, распространение ресурсов/среды, гекс-карта поверхности радиуса 2/3/4 по размеру планеты (`generateSurface`) и распределение ресурсов по гексам (`distributeHexResources` — фон+месторождения для металлов/газов, привязка к биому для воды/биогенных), ТЗ.md §2.5. `Planet.Stock map[string]float64` — склад колонии (сырьё+компоненты в одном словаре), заполняется/расходуется посуточно `server/production.go`, пустой у неколонизированных планет. 16-й ресурс — металлический водород (`resourceDefs`, ТЗ_Ресурсы.md §3.1): только газовые гиганты, только зоны 1–4 (резкий позиционный гейт `metalHydrogenMaxR`, не пологий galMod), только у синих гигантов/нейтронных звёзд (starType) — редкость подобрана эмпирически так, чтобы запас/спрос был ниже, чем у битумов. **Солёная/пресная вода** (ТЗ_Ресурсы.md §2, «Солёная и пресная вода») — `water_ice` как ресурс считается только с пресной воды, по требованию пользователя: новое поле `SurfaceHex.Fresh`/`SurfaceHexDetail.Fresh` (JSON `fresh`), вычисляется постфактум функцией `markFreshWater` сразу после генерации типов гексов в `generateSurface` (не может делаться в основном цикле генерации — там ещё не известны типы соседей). Правило: `icecap` — всегда пресная; гекс `water` с хотя бы одним соседним `water` — море/океан (солёная, НЕ пресная); гекс `water` без соседей-воды — изолированное пресное озеро; гекс ЛЮБОГО типа по соседству (1 кольцо, `hexNeighbors` — buildings.go) с уже пресным источником — тоже пресный (родники/сток). Заодно `icecap` теперь выпадает не только по широте (полюса) — гора где угодно на планете может стать ледником на вершине (тот же гейт по гидросфере, шанс ниже в жарких широтах, не ноль). `hexBioWeight` для `waterIce` — 3.0 icecap / 1.0 пресное озеро / **0 солёное море-океан** (раньше все "water" весили одинаково) / 0.3 рядом с пресным источником / 0.05 фон (вечная мерзлота) везде остальном. **Гелий-3** — по требованию пользователя (уточнено дважды за сессию: сперва «всегда концентрирован», потом поправлено на «зависит от атмосферы», земной/лунный пример пользователя) выделен из общего `distributeUniformDeposits` для `catGas` в `distributeHexResources`, теперь по признаку `hasAtmo` (`pressure >= atmoThreshold`, константа вынесена на уровень пакета — нужна и `generateSurface`, и `distributeHexResources`, поэтому оба принимают `pressure`/`pt` параметрами): атмосферная планета («Земля») — 0.45 фон / 3 месторождения, без тяготения к горам, рассеян как обычный газ, месторождений не образует; безатмосферная («Луна») — 0.08 фон / всего 2 месторождения / тяготение к горам (`preferMountain=true`), заметно копится в реголите локально. Газовые гиганты не затронуты вовсе — у них нет гекс-карты (`generateSurface` возвращает nil для `pt=="gas"`), их гелий-3 — один общий на планету параметр. **Силикаты** — по требованию пользователя тоже переведены с фона+месторождений на честную привязку к биому (`distributeBiomeCorrelated`/`hexBioWeight`, тот же механизм, что вода/биомасса): горы ×2.5, холмы ×1.6, лёд ×0.5, море/океан ×0.3 (солёное или пресное озеро — без разницы, порода одинаково накрыта водой), везде остальном — базовый вес ×1.0. **Тугоплавкие металлы** (`refractory`) — по требованию пользователя выделены из общего `catMetals` (0.20 фон/4 месторождения) в собственный, ещё более концентрированный случай: 0.05 фон / 4 месторождения (95% запаса в 4 гексах на тестовом прогоне) — КРОМЕ голых ядер (`pt=="core"`), где явно противоположное правило: 1.0 фон / 0 месторождений, полностью равномерно (мантийный/ядерный элемент, однородный по всей обнажённой породе — поверхностные жилы образует гидротермальная/вулканическая активность КОРЫ, которой у голого ядра нет). **Вулканические газы** (`volcanicGases`) — по требованию пользователя выделены из общего `catFuel` (делил с водородом, `preferMountain=false` — вообще без тяготения к горам) в отдельный случай через `distributeBiomeCorrelated`: горы ×4.0, холмы ×1.5, везде остальном ×0.2 (та же тектоника, что и горообразование, `tectonic` в generateSurface). После аудита остальных ресурсов по прямому запросу пользователя (радиоактивные — уже были корректно смоделированы месторождениями, не трогались) — ещё 2 правки: **платиноиды** — очень высокая концентрация (`rd.Key == "platinoids"`, отдельно от общего `catMetals`): 0.02 фон / 2 месторождения («пара», самая низкая Rarity среди catMetals — 0.03, втрое реже тугоплавких, реальные платиноиды — самая концентрированная руда из существующих), 98% запаса в топ-2 гексах на тестовом прогоне; **железо** — присоединено к силикатам в `distributeBiomeCorrelated`, тяготеет к горам мягче силикатов (×2.0 горы / ×1.3 холмы / ×1.0 везде остальном, вода не тронута — не просили). Заодно `distributeBiomeCorrelated` получила `rng`-параметр и небольшой шум по гексу (0.85–1.15× поверх веса биома, по требованию пользователя — «небольшой разброс, но учесть типы гексов»): раньше все гексы ОДНОГО типа получали абсолютно идентичное значение (hexBioWeight детерминирован, никакого шума не было) — теперь тип задаёт средний уровень, а не единственное число; это касается ВСЕХ 8 ресурсов на биомной модели (вода, силикаты, железо, вулканические газы, биомасса, фосфаты, карбонаты, битумы) одним изменением функции, не только новых. **Точное сохранение суммы при раздаче по гексам** (`largestRemainderAllocate`, метод наибольшего остатка/Hare-Niemeyer, по прямому требованию пользователя — «проверь что сумма ресурсов на планете распределённая на гексах сходится с контрольной»): раньше и `distributeUniformDeposits`, и `distributeBiomeCorrelated` округляли долю КАЖДОГО гекса независимо (`math.Round`), из-за чего при низком общем запасе ресурса, размазанном по многим гексам, бо́льшая часть долей (<0.5) независимо округлялась вниз до нуля — диагностический тест на реальных планетах вскрыл потерю до 15–22% общего запаса у дефицитных ресурсов (лёгкие редкие/тугоплавкие/радиоактивные) при почти идеальном совпадении у обильных (силикаты/железо, доля на гекс много больше 0.5). Теперь обе функции сначала берут `floor` от доли каждого получателя, а «сдачу» (total минус сумма floor) раздают по одной единице тем, у кого наибольшая дробная часть — сумма по гексам после этого ТОЧНО (не приблизительно) равна `Planet.Res[key]`, перепроверено тем же диагностическим тестом (6 планет разных типов звёзд, все расхождения = 0).
  - `server/ship.go` — корабль игрока: один глобальный объект на сервере (пока нет аккаунтов), реальное время полёта (не игровые месяцы), навигация/посадка/взлёт (ТЗ.md §2.7.1). Посадка на газовые гиганты отклоняется — твёрдой поверхности нет.
  - `server/buildings.go` — здания и транспортная сеть колонии (ТЗ_UI.md §5.3, ТЗ_Экономика.md §§12/15): модель `Building`, связность гексов (`connectedHexes`, BFS от домашнего гекса), стартовая колонизация 4 столичных планет (`bootstrapColony` — шахты на богатейшие гексы, транспортные узлы мостят разрывы). Только размещение/связность — сама добыча/производство/содержание/рост населения теперь в `server/production.go` (см. ниже), этот файл их не считает, только даёт данные (`starterMineGroups`, `connectedHexes`, `planetFoodTypes`, `settlementWorkerCap`), которые тот переиспользует. `computePopulation` по-прежнему заселяет колонию один раз при бутстрапе по лимиту разнообразия пищи (ТЗ_Экономика.md §11.2: число Жилых модулей × 5/7/9 в зависимости от того, сколько из 3 типов пищи колония способна производить по составу зданий; стандартная колония производит все 3 → 10×9=90) — это посевное значение на день 0, дальше population эволюционирует посуточно в production.go теми же формулами. **Энергопотребление зданий колонии теперь реализовано** (по прямому требованию пользователя — «добавь учёт дефицита энергии»): `Planet.EnergyProduction`/`EnergyConsumption` пересчитываются посуточно `energyDay` (production.go, см. ниже) по подключённым зданиям, `client/planet.html` `conStats()` теперь читает эти настоящие числа вместо собственного клиентского подсчёта по всем зданиям планеты без разбора связности (клиентская формула осталась только запасным вариантом, если поле почему-то отсутствует). Дефицит энергии сам по себе пока ни на что не влияет (не блокирует добычу/производство/содержание) — чистая метрика для игрока. `BuildingNuclearPlant` (`nuclear_plant`, «Атомная станция») — новый тип здания (по требованию пользователя, ТЗ_Экономика.md §12.2/§13/§14.2, раньше существовала только в ТЗ как теория без `BuildingType`): +40 энергии/сутки (`energyDay`), 1 штука в `starterInfra` на каждую из 4 столиц (сверх «стандартной колонии» ТЗ_Экономика.md §12, там 0 штук). Потребление энергии — по прямому требованию пользователя ДИФФЕРЕНЦИРОВАННОЕ, не единая ставка 1/здание (полный разбор — `production.go`, `isActivityBilledEnergy`/`ActivityEnergySpent`): добыча и «прочее» — 1/сутки как раньше; заводы платят по факту партии (ТУ1=1/ТУ2=2/ТУ3=3 энергии); завод переработки — фиксированные 5/партию. `BuildingRecycler` (`recycler`, «Завод переработки») — ещё одно новое здание (по прямому требованию пользователя — «переработка отходов»): перерабатывает избыток сырья (Силикаты/Карбонаты обычно скапливаются тысячами) в дефицитное (Битумы) или редкое (Лёгкие редкие металлы/Платиноиды) сырьё, рецепты — `recyclingRecipes` (economy.go), обработка — `recycleHour` (production.go, раз в 2 игровых часа, не раз в час, как обычное производство). 1 штука в `starterInfra` на колонию — тот же принцип добавления, что у атомной станции. `bootstrapColony` теперь также заполняет `Planet.Stock` стартовым запасом по 10 каждого из 21 компонента (по требованию пользователя — иначе склад в день 0 пуст по всем компонентам сразу, см. `demolitionGraceDays` в production.go). `Planet.Capital` (planets.go) — флаг, ставится в `forceHabitableCapitals` (main.go) вместе со стартовой колонизацией; клиент (`World.planetLabel`, world.js) по нему подписывает планету «Столица <Фракция в род. падеже>» вместо обычного названия по типу — используется в `planet.html`/`system.html`/`ship.html`/админ-`planets.html` (там же бейдж с населением/числом зданий, чтобы разом видеть все 4 колонии).
  - `server/production.go` — цикл колонии (ТЗ_Экономика.md §§2–15): добыча → содержание → производство → население. Добыча/содержание/сброс суточного счётчика партий/население — раз в игровые сутки (`runProductionDay`); производство — раз в игровой ЧАС (`runProductionHour`/`produceHour`, решение пользователя: не «пока хватает сырья за раз», как было изначально, а РОВНО ОДНА партия за час, не больше `maxProductionBatchesPerDay=12` партий/сутки на завод — 120 компонентов/сутки максимум с одного здания). «Час»/«сутки» — понятия, которых в игре раньше не было нигде (`Clock`, clock.go, знает только непрерывный `months`): `daysPerMonth = 365.2425/12` (та же калибровка, что `gameSpeedRealtime`), `hoursPerDay = 24`; `advanceProduction` — ЕДИНЫЙ почасовой догоняющий цикл (не два независимых счётчика дня/часа — риск рассинхронизации), день выводится как `lastProdHour % hoursPerDay == 0`, на этот час `runProductionDay` вызывается СТРОГО ПЕРЕД `runProductionHour` (новые сутки — чистый счётчик партий и свежедобытое сырьё раньше первого часа производства); `maxProductionHoursPerAdvance` — предохранитель от шторма после долгой паузы/ускорения. Изолированные (не `connectedHexes`) здания не участвуют ни в одном шаге — то же самое уже обещала подпись в `planet.html` («⚠ изолирован — не поставляет ресурсы на склад»), теперь это правда. Добыча (`mineDay`) — ТЗ_Экономика.md §2 буквально: шахта выдаёт добычу, равную концентрации своего гекса, за сутки (гекс не истощается, как и раньше `Planet.Res`); ключи ресурсов на тип здания — `starterMineGroups` (buildings.go), не задваивается. Содержание (`upkeepDay`) — `buildingUpkeep` (ТЗ_Экономика.md §14.2 + §15.3, 20 типов × 3 статьи расхода, включая «Атомную станцию» — см. ниже). **Демонтаж при нехватке содержания** (по прямому требованию пользователя — раньше нехватка была просто недоплатой без последствий): если на складе не хватает хотя бы ОДНОЙ из 3 статей расхода (`canAffordCycle`), здание не платит частично — счётчик `Building.MissedUpkeepDays` растёт; после `demolitionGraceDays=3` суток подряд без полной оплаты здание демонтируется — `refundBuilding` возвращает игроку `demolitionRefundFrac=60%` стоимости постройки (`buildingCostByType`, economy.go, округление `math.Round` ПО КАЖДОМУ компоненту рецепта отдельно), остальные 40% утилизируются безвозвратно. Успешная оплата в любой день сбрасывает счётчик в 0 — порог именно про ХРОНИЧЕСКИЙ дефицит. Грейс-период в 3 суток — САМОСТОЯТЕЛЬНОЕ решение сверх явного запроса: демонтаж на первую же неудачу снёс бы стартовую колонию целиком в первые же игровые сутки, потому что `runProductionDay` (и значит `upkeepDay`) вызывается СТРОГО ПЕРЕД первым же `runProductionHour` той же границы суток — день 0 застаёт склад пустым по всем произведённым компонентам (Химреагенты/Полимеры/Металлоконструкции и т.д. — сами продукты заводов, не сырьё) ещё до того, как производство вообще успело хоть раз отработать. Стресс-тест (60 игровых суток, все 4 реальные столицы, временный `zz_demolition_test.go`) подтвердил и что грейс-период работает как задумано, и что даже с ним колонии реально коллапсируют почти полностью за ~2 месяца: узкое место — Битумы (`bitumens`), которых физически не хватает на добыче, поэтому Полимеры (`polymers`, вход почти в каждое здание, 9 битумов/цикл) практически никогда не накапливаются, а Полимеры/Химреагенты нужны в upkeep почти всех 20 типов зданий, включая сами заводы (Химзавод/Металлзавод/Электрозавод/Лаборатория) — это необратимая смерть-спираль: без заводов новые компоненты произвести вообще нечем. Пользователь подтвердил, что это ожидаемый и желаемый результат («колония большая и не может жить автономно») — правка НЕ смягчалась, поведение оставлено как есть. Производство (`produceHour`) — какой из рецептов завода производить в конкретный час выбирает `pickRecipeToProduce`, все 3 уровня ТУ сразу доступны заводу (у `Building`/`BuildingType` нет поля уровня технологии, апгрейдить пока нечего, это допущение v1). **Очередь производства — `Building.Queue` теперь реально читается, не просто структура данных** (третий пересмотр приоритета производства в сессии — история: 1) плоская почасовая ротация → 2) приоритет по ТУ → 3) «минимум по разнообразию, потом избыток по ТУ», `Приоритет_производства_по_ТУ.md` — все три версии устарели, заменены целиком по прямому требованию пользователя: «алгоритм должен работать так: сначала считаем что нужно для содержания, потом производим в первую очередь то что нужно для содержания колонии, потом смотрим чего на складах меньше минимума и строим это, потом строим то что как можно выше по цене, остаток лишних ресурсов перерабатываем... у нас есть очередь производства, управляем ей, формируем её буквально»). Очередь пересчитывается РАЗ В СУТКИ (`buildDailyQueues`, вызывается в `runProductionDay` после `upkeepDay`/`energyDay` — чтобы видеть ИТОГОВЫЙ состав колонии на конец дня и свежий склад), а не каждый час — `produceHour`/`recycleHour` внутри часа просто идут по `b.Queue` СТРОГО ПО ПОРЯДКУ (первый по карману побеждает), больше никакой почасовой ротации по `hourSeed` (параметр остался в сигнатурах ради `production_test.go`, внутри не используется). Очередь ОБЩАЯ НА ВЕСЬ ТИП ЗАВОДА (решение пользователя, из выбора в `AskUserQuestion`) — одинаково записывается во все здания одного `BuildingType`, не считается отдельно для каждого. Три приоритетные группы, без пересечения (`buildQueueForRecipes`):
1. **Нужно для содержания** — `dailyUpkeepDemand` суммирует `buildingUpkeep` по всем подключённым зданиям на сутки; рецепт сюда попадает, если его выход входит в этот спрос И на складе меньше этой суточной потребности; сортировка внутри группы — по размеру нехватки, самый острый дефицит первым.
2. **Ниже общего минимума** — то же самое, что раньше делала `pickBelowFloor` (`componentStockFloor=10`, не убран), но теперь явный порядок, не ротация; сортировка — по размеру нехватки до порога.
3. **Всё остальное — по НАСТОЯЩЕЙ цене** (решение пользователя, выбрано явно вместо уровня ТУ через `AskUserQuestion`): `priceOf` (economy.go) — резолвер `resolveComponent`/`resourcePrice`, тот же, что считает цены для `/api/economy`, кеш на один пересчёт очереди (`priceCache`), от дорогого к дешёвому.

Завод переработки получает очередь тем же вызовом, но БЕЗ фаз 1/2 (`recyclingRecipes` производят СЫРЬЁ, не входящее в `buildingUpkeep` готовых компонентов) — его очередь всегда `recyclingRecipes` в порядке объявления, что и реализует «переработка — последним шагом» (решение пользователя, выбрано явно через `AskUserQuestion` — встроить в общий приоритет, а не оставлять отдельным процессом): раньше `recycleHour` был гейтнут чётностью часа (партия раз в 2 часа), теперь работает в ТОМ ЖЕ почасовом цикле, что и обычные заводы, никакой особой частоты. `Building.BatchesToday int` — счётчик партий за текущие сутки, сброс — `resetDailyBatches` на границе суток, без изменений. **Журнал событий** (`Planet.EventLog`, по требованию пользователя — «журнал записей всех компонентов и действий на колониях... в табличном виде хранит действия производства, сносы, приход, убыль и остаток всех ресурсов за цикл»): кольцевой буфер (`maxEventLogDays=60`) записей `DayLogEntry` — добыто/произведено/потрачено/снесено/остаток на конец суток, накопители `Planet.Mined/Produced/ConsumedToday`/`DemolishedToday` растут весь день в `mineDay`/`upkeepDay`/`produceHour`/`recycleHour`, сворачиваются в новую запись `logDayEntry` последним шагом `runProductionDay`. НЕ едет в `/api/galaxy` (`json:"-"`, тот опрашивается раз в секунду — лог за 60 суток раздул бы его) — отдельный эндпоинт `GET /api/planet/log?starId=&planetIndex=` (main.go), который читает новая страница `client/colony-log.html` (переход из админ-панели, «ЖУРНАЛ КОЛОНИИ →», `admin-panel.js`): выбор одной из 4 столиц, таблица по суткам (новые сверху), имена ресурсов/компонентов — из `/api/economy`, тот же приём, что `whResInfo`/`whItemName` в `planet.html`. Население (`populationDay`) — ТЗ_Экономика.md §11.2 буквально: ±1 житель/поселение/сутки по еде (`Stock["biomass"]+Stock["biosynthetics"]+Stock["bioengineered"]`, порядок списания — от дешёвого к дорогому), жёсткий потолок посёлок×10; решение пользователя — эта формула, а не пометка ТЗ.md §2.10 «прирост не моделируется» (вахтовый метод), тот документ в этой части устарел. Энергия (`energyDay`) — по требованию пользователя («добавь учёт дефицита энергии»), вызывается ПОСЛЕ `upkeepDay` (баланс должен отражать состав колонии на КОНЕЦ суток, после возможного демонтажа, а не до). `EnergyProduction` — `buildingEnergyOutput` (10 у Водородного генератора, 5 у Солнечной панели, 40 у Атомной станции, ТЗ_Экономика.md §12.2). `EnergyConsumption` — по прямому требованию пользователя ДИФФЕРЕНЦИРОВАННОЕ, не единая ставка (раньше было 1/здание без исключений): добыча и «прочие» здания (`isActivityBilledEnergy`==false) — по-прежнему 1/сутки за штуку; заводы (`factoryBuildingName`) и завод переработки (`BuildingRecycler`) ИСКЛЮЧЕНЫ из этой плоской суммы целиком (не 1+тариф, а ВМЕСТО 1) — их расход копится весь день в `Planet.ActivityEnergySpent` (planets.go): `produceHour` добавляет тариф по ТУ произведённого рецепта (1/2/3 — решение пользователя «Производство — ТУ1 1 энергии, ТУ2-2, ТУ3-3»), `recycleHour` — фиксированные `recyclingEnergyPerBatch=5` за любую партию переработки. `energyDay` складывает накопленное в `EnergyConsumption` и обнуляет `ActivityEnergySpent` для следующих суток (тот же принцип, что `Building.BatchesToday`/`resetDailyBatches`, только агрегатно на уровне планеты, не по зданиям). Результат — числа на `Planet` (planets.go), пока ни на что не влияющие (не блокирует добычу/производство/содержание), чистая метрика для игрока. **Переработка излишков** (`recycleHour`, по прямому требованию пользователя — «переработка отходов... с большими затратами энергии») — отдельный от `produceHour` почасовой шаг, партия РАЗ В ДВА ЧАСА (`hourSeed%2==0`), не каждый час: `recyclingRecipes` (economy.go, 3 рецепта, СВОЯ нумерация Tier 1/2/3 — приоритет переработки, не уровень ТУ componentRecipes) перебираются в ФИКСИРОВАННОМ порядке объявления (не «минимум по разнообразию», как обычное производство) — рецепт 1 (дешёвый, Силикаты 5 + Карбонаты 25 + Дикая биомасса 125 → Битумы 10, пропорция намеренно НЕ равная — по требованию пользователя приближена к реальной химии: битумы почти целиком углерод, Карбонаты — буквальный источник углерода, Биомасса — готовые C-H связи, Силикаты — не сырьё, а катализатор/подложка в следовых количествах, силикагель реально используют носителем катализатора в синтезе Фишера-Тропша) почти всегда по карману и потому почти всегда побеждает; рецепты 2/3 (низкорентабельные — по требованию пользователя «чтобы привозить извне было выгодней») включаются, только когда у рецепта 1 кончилось своё сырьё: рецепт 2 — 1000 Силикатов + 50 Химреагентов → всего 5 Лёгких редких металлов, рецепт 3 — 2000 Силикатов + 500 Карбонатов + 100 Химреагентов → всего 2 Платиноида (`recyclingBatchOutput` — намеренно МЕНЬШЕ обычной партии в 10, «по немножку», решение пользователя). Все количества согласованы с пользователем построчно, не из ТЗ. **Занятость населения на зданиях** (по требованию пользователя, уточнено через `AskUserQuestion` — из нескольких прочтений неоднозначного «реализовать потребление после производства» выбрана именно проверка свободного/занятого населения): `buildingWorkerRequirement(t BuildingType) int` — 1 работник на любое здание, КРОМЕ Жилого модуля и Транспортного узла (0, они не производят и не добывают); `workerPriority(t BuildingType) int` — 0 у 4 добывающих типов (mine/atmo_collector/bio_extractor/hydro_farm), 1 у 4 заводов (factory_metal/factory_chem/factory_elec/lab), 2 у всего остального (это порядок распределения, из ТЗ не следует — самостоятельное архитектурное решение, не запрошено явно); `assignedWorkers(p *Planet, connected map[[2]int]bool) map[int]bool` — сортирует подключённые здания-кандидаты по приоритету (внутри приоритета — по исходному порядку `p.Buildings`) и раздаёт `p.Population` работников по одному, пока не кончится либо население, либо кандидаты. **Возвращает `map[int]bool`, ключ — ИНДЕКС здания в `p.Buildings`, не координата гекса** — на одном гексе может стоять до 7 зданий (`hexSlotsCap`, buildings.go), поэтому ключ-координата ошибочно слил бы занятость разных зданий одного гекса в один флаг (обнаружено диагностическим тестом при искусственном урезании населения — суммы по типам не сходились с размером map). `mineDay` и `produceHour` пропускают здание, если оно не в `assigned` (недостаточно населения — простаивает так же, как при разрыве связности); `upkeepDay` **сознательно НЕ гейтится** занятостью — содержание платится независимо от того, укомплектовано ли здание работником (так же, как Жилой модуль в принципе не требует работника, но исправно потребляет ресурсы на содержание). Конкурентность: `sim.go` документирует объекты как неизменные после создания (`Sim.Snapshot()`/`Sim.Object()` отдают указатели, которые маршалятся в JSON уже после отпускания блокировки) — общий обход `forEachColonizedPlanet` (используют и `runProductionDay`, и `runProductionHour`) не мутирует `Planet` на месте, а клонирует срез планет звезды и подменяет `sim.objects[id]` целиком под `sim.mu.Lock()`, по образцу `Sim.Advance`; `Planet.Stock` (map) клонируется отдельно (`cloneStock`) — поверхностное копирование среза `Planet` расшарило бы старую map с новой. Экономика (`ensureEconomy()`) теперь подгружается сразу при открытии страницы, а не только по клику «Настроить модули» — иначе масса/энергетика в этих новых сводках сперва показывали 0. Над списком карточек — «Средние показатели по классам» (`renderClassAverages`, заменила прежний большой текст-пояснение): группировка по бракету `classFor()`, для каждого класса — число кораблей в библиотеке, средние масса/прочность/масса модуля/число свободных слотов, приведённая масса (масса, если все свободные слоты занять модулями средней массы класса), среднее число двигателей, средние выработка/расход энергии на ускорении; пересчитывается при любом изменении любого корабля. Кнопка «+ ДОБАВИТЬ КОРАБЛЬ» — библиотека не ограничена стартовыми 20. **Никакого `localStorage`** — единственное хранилище библиотеки сразу `/api/ship-defaults` (`server/shipdefaults.go`): страница при открытии читает состояние оттуда (`loadFromStorage`, имя оставлено по истории, по факту грузит с сервера), каждое изменение (клик по клетке/модуль/название/очистить/залить/добавить) с дебаунсом 400мс пишет туда же весь набор целиком (имя + занятые палубы: row/col + модули, только карточки хотя бы с одной палубой). Раньше был отдельный слой `localStorage` с фоновой «подсинхронизацией» на сервер — из-за двух копий состояние могло разойтись и не было понятно, подтянулось ли на самом деле; по прямому требованию пользователя («сделай прямую синхронизацию, а не через костыли») убран целиком, сервер — единственная версия правды, никакого отдельного шага синхронизации с Верфью на планете не требуется. Кнопка «Экспорт JSON» — отдельный ручной бэкап (полная раскладка с секторами/энергетикой), не участвует в этой синхронизации.
- `archive/` — прежняя версия проекта целиком (не трогать без необходимости переиспользовать конкретную сущность):
  - `archive/docs/` — прежние ТЗ (галактическая симуляция, экономика, планетарный UI, цены, реестр звёзд).
  - `archive/server/` — прежний рабочий прототип (Go-сервер + фронтенд), включая данные симуляции (`star_registry.json`, `scans/`) и сборку `ouroboros.exe`.
  - `archive/tools/` — PowerShell-скрипты анализа реестра звёзд старой версии (пути внутри — относительно `$PSScriptRoot`).
  - `archive/assets/` — референсные изображения старой версии (спрайты кораблей и т.п.).
  - `archive/CLAUDE.md` — старые инструкции, актуальные только в контексте archive/server.

В корне проекта держим только актуальную v2: ТЗ, `server/`, `client/`, `assets/` (пустой каркас под ассеты v2). Всё, что относится к прежней версии, живёт в `archive/`.

## Архитектура v2

Симуляция — на сервере, клиент только отображает. Разыгрывать что-либо на клиенте нельзя: два устройства должны видеть одну и ту же галактику. Всё игровое время идёт от сервера; ускорение для тестов — серверный множитель (месяцев в реальную секунду), а не локальная настройка браузера.
